CHAPTER OVERVIEW

ทำไมต้องวัด "ประสิทธิภาพ"?

TWO KINDS OF PERFORMANCE

ประสิทธิภาพมี 2 แบบ — ที่คนมักสับสน

ตัวอย่าง: เครื่องบิน 2 ลำ บินจากวอชิงตัน ดีซี ไปปารีส — ลำไหน "เร็วกว่า"? ขึ้นอยู่กับว่าคุณสนใจอะไร

เครื่องบินเวลาบินความเร็วสูงสุดผู้โดยสารคนที่ส่งได้ต่อชั่วโมง
Boeing 7476.5 ชม.610 mph470 คน286,700
Concorde3 ชม.1350 mph132 คน178,200

คุณเป็นผู้โดยสาร 1 คน

อยากถึงเร็วที่สุด → สนใจ Concorde (ใช้เวลาน้อยกว่า 3 ชม. vs 6.5 ชม.)

คุณเป็นสายการบิน

อยากขนคนให้ได้เยอะที่สุดต่อวัน → สนใจ Boeing 747 (286,700 vs 178,200 คน/ชม.)

ในคอมพิวเตอร์ก็เหมือนกัน:
Response Time (Execution Time) = เวลาทำ "งานเดียว" ให้เสร็จ · Throughput (Bandwidth) = จำนวนงานที่เสร็จต่อหน่วยเวลา — สองอย่างนี้ไม่ใช่สิ่งเดียวกัน บางทีก็สวนทางกัน

DEFINITION

นิยาม "Performance" แบบคณิตศาสตร์

กติกา: ตัวเลขยิ่งมาก ยิ่งดี (bigger is better) — ถ้าสนใจ response time เขานิยามว่า...

performance(x) = 1 / execution_time(x)
เครื่องที่ใช้เวลาน้อย = performance สูง (กลับเศษกลับส่วนกัน)
"F เร็วกว่า S อยู่ n เท่า" หมายถึง
n = performance(F) / performance(S) = execution_time(S) / execution_time(F)
ทำไมต้องกลับเศษ? เพราะ performance ใหญ่ ⇔ เวลาน้อย — การเทียบ ratio ของเวลาเลยตรงไปตรงมาที่สุด
ตัวอย่าง: F ใช้ 5 วินาที S ใช้ 10 วินาที → F เร็วกว่า 10/5 = 2 เท่า

WORKED EXAMPLE

เครื่องบิน — "เร็วกว่ากี่เท่า" เปลี่ยนไปตามสิ่งที่วัด

คำตอบเปลี่ยนไปตามว่าเรากำลังพูดถึง performance แบบไหน

เทียบ Response Time (เวลาบิน)

1. Concorde ใช้ 3 ชม. · Boeing 747 ใช้ 6.5 ชม.
2. n = time(747) / time(Concorde) = 6.5 / 3
3. = 2.17 ≈ 2.2 เท่า — Concorde เร็วกว่า

เทียบ Throughput (คนต่อชั่วโมง)

1. 747: 286,700 · Concorde: 178,200 คน/ชม.
2. n = 286,700 / 178,200
3. = 1.6 เท่า — Boeing 747 ชนะ
อย่าพูด "X% เร็วกว่า" ลอย ๆ — ต้องบอกชัดว่าเรากำลังปรับปรุง execution time หรือ performance ตัวไหน จะกำกวมน้อยกว่า

TIME DEFINITIONS

"เวลา" ในคอมพิวเตอร์มีหลายความหมาย

บทนี้เน้นวิเคราะห์ CPU time เพราะวัดฝีมือของตัว CPU ได้ตรงกว่า (ไม่ปนกับว่า OS จัดคิวดีหรือแย่)

Real / Response / Elapsed time

เวลาทั้งหมดที่ผ่านไปจริง รวมทุกอย่าง — รอ disk, รอ I/O, รอ OS จัดคิว ฯลฯ

CPU time

เฉพาะเวลาที่ CPU ทำงานให้โปรแกรมของคุณจริง ๆ — เพราะในเครื่องจริงมีหลายโปรแกรมแย่งคิว CPU กัน

CPU time แบ่งย่อยคืออะไร
User timeเวลาที่โปรแกรมของคุณทำงานเอง
System timeเวลาที่ OS ทำงานแทน (เรียกใช้ kernel)
จำแบบนี้Elapsed time = รวมทุกอย่าง · CPU time = เฉพาะ CPU · CPU time = User + System

CLOCK

หน่วยวัดเวลาใน CPU — Clock Cycle

CPU มี "นาฬิกา" เดินเป็นจังหวะคงที่ — ทุก ๆ การทำงานในฮาร์ดแวร์ขยับตามจังหวะนี้ ช่วงแต่ละจังหวะเรียกว่า clock cycle

Clock Cycle Time

เวลาต่อ 1 จังหวะ เช่น 2 นาโนวินาที (ns)

Clock Rate (Clock Speed)

จำนวนจังหวะต่อวินาที เช่น 500 MHz — เป็น ส่วนกลับ ของ cycle time (เลข GHz บนกล่อง CPU)

Clock Rate = 1 / Clock Cycle Time   ⇔   Clock Cycle Time = 1 / Clock Rate
เช่น 500 MHz → 1 ÷ (500×10⁶) = 2×10⁻⁹ = 2 ns
จับมือแปลง: clock rate 2 GHz → CT = 1 ÷ (2×10⁹) = 0.5×10⁻⁹ = 0.5 ns
จำหน่วย: 1 MHz = 10⁶ Hz · 1 GHz = 10⁹ Hz · 1 ns = 10⁻⁹ วินาที

KEY FORMULA · STEP 1

สูตรหัวใจของบทนี้: CPU time

ขั้นที่ 1 — เริ่มจากจำนวน clock cycles ที่ใช้ทั้งหมด คูณด้วยเวลาแต่ละจังหวะ

CPU execution time = จำนวน Clock Cycles ทั้งหมด × Clock Cycle Time
ทำไมต้องคูณ? 1 รอบใช้ CT วินาที → ถ้าใช้ทั้งหมด N รอบ ก็ต้องใช้ N × CT วินาที (เหมือนงาน 10 ชิ้น ชิ้นละ 2 ชั่วโมง = 20 ชั่วโมง)
ตรวจหน่วย: รอบ × (วินาที/รอบ) = วินาที ✓
แต่ยังใช้ไม่ได้จริง เพราะเรายังไม่รู้ว่า "จำนวน clock cycles" มาจากไหน — ไปดูขั้นที่ 2 ต่อเลย

KEY FORMULA · STEP 2 ⭐⭐⭐

สูตรที่สำคัญที่สุดของทั้งบท

"จำนวน clock cycles" มาจาก Instruction Count × CPI

Instruction Count (IC)

โปรแกรมนี้มีกี่คำสั่งทั้งหมด — ขึ้นกับว่าเขียนโค้ดยังไง คอมไพล์ยังไง

CPI — Cycles Per Instruction

โดยเฉลี่ย 1 คำสั่งใช้กี่ clock cycle — ขึ้นกับว่า CPU ออกแบบมาดีแค่ไหน

CPU time = Instruction Count × CPI × Clock Cycle Time
CPU time = (คำสั่ง/โปรแกรม) × (รอบ/คำสั่ง) × (วินาที/รอบ) = วินาที / โปรแกรม
หน่วยตัดกันจนเหลือแค่ "วินาที" พอดี ✓
ต้องรู้ครบทั้ง 3 ตัว ถึงจะทำนายเวลาได้จริง — ขาดตัวใดตัวหนึ่งไปจะเดาไม่ถูกเลย

WARNING ⚠️

Megahertz Myth — GHz เยอะ ≠ เร็วเสมอ

performance ไม่ได้ขึ้นกับปัจจัยเดียว — เลข MHz/GHz อย่างเดียวไม่ได้บอกอะไรทั้งหมด

CPUClock RateCPIเวลา/คำสั่ง (CPI ÷ rate)
เครื่อง A3 GHz (เยอะกว่า!)22 ÷ 3 GHz = 0.667 ns
เครื่อง B2 GHz11 ÷ 2 GHz = 0.5 ns ← เร็วกว่า!
บทเรียน: CPU ที่ clock rate สูงมากอาจช้ากว่าเครื่องที่ clock rate ต่ำกว่า ถ้า CPI แย่กว่ามาก หรือ Instruction Count เยอะกว่ามาก
ข้อสอบที่ชอบถาม: "IC เท่ากัน เครื่องไหนเร็วกว่า" → คำนวณ CPI ÷ clock rate (หรือ CPI × CT) ต่อคำสั่ง แล้วเทียบกัน
Exam Tipอย่าดูแต่ GHz — ใช้สูตร CPU time = IC × CPI × CT เทียบครบทุกตัวเสมอ

MEASUREMENT

แต่ละตัวเลขวัดได้ยังไงจริง ๆ?

วิธีหาค่าของแต่ละปัจจัยในสูตร CPU time

ปัจจัยวิธีหาค่า
Clock Cycle Timeดูจาก spec เครื่อง (คือค่า clock rate ที่โฆษณาไว้)
Instruction Countนับคำสั่งในโปรแกรม · ใช้โปรแกรมจำลอง (simulator) · หรือ hardware counter ในตัว CPU
CPIคำนวณจาก (Execution Time ÷ Clock Cycle Time) ÷ Instruction Count หรือดูจาก hardware counter
หา CPI อีกวิธี — ถัวเฉลี่ยถ่วงน้ำหนัก (weighted average) ดูสไลด์ถัดไปเลย

WEIGHTED CPI ⭐⭐⭐

CPI ถัวเฉลี่ยถ่วงน้ำหนัก

คำสั่งแต่ละประเภทใช้จำนวน cycle ไม่เท่ากัน → หา CPI รวมโดยคูณความถี่ แล้วบวกรวม

ขั้น 1 หา CPI ของคำสั่งแต่ละประเภท
ขั้น 2 หา % ความถี่ที่แต่ละประเภทถูกใช้
ขั้น 3 คูณกัน (Freq × CPI) แล้วบวกรวมทุกประเภท
ประเภทคำสั่งความถี่ (Freq)CPIFreq × CPIสัดส่วนเวลาที่ใช้จริง
ALU50%10.523%
Load20%51.045%
Store10%30.314%
Branch20%20.418%
รวม100%CPI = 2.2100%
ออกข้อสอบ!CPI รวม = Σ(freq × CPI) = 0.5 + 1.0 + 0.3 + 0.4 = 2.2 · สัดส่วนเวลา = (freq × CPI) ÷ CPI รวม

INSIGHT 💡

"ใช้บ่อย" ≠ "กินเวลาเยอะ"

จากตารางที่แล้ว — จุดที่น่าสนใจที่สุดของบทนี้

สัดส่วนเวลารวม 100% (ใครกินเวลาเท่าไร)
ALU 23%
Load 45%
Store 14%
Branch 18%

ALU — ใช้บ่อยแต่เร็ว

ถูกใช้บ่อยที่สุด (50% ของคำสั่ง) แต่กินเวลารวมแค่ 23% เพราะแต่ละคำสั่งเร็วมาก (CPI = 1)

Load — ใช้ไม่บ่อยแต่ช้า

ใช้แค่ 20% ของคำสั่ง แต่กินเวลาถึง 45% เพราะแต่ละคำสั่งช้ามาก (CPI = 5)

บทเรียนสำคัญต้องดูทั้ง "ความถี่" และ "CPI" ประกอบกัน ถึงจะรู้ว่าควรไปปรับปรุงส่วนไหนของ CPU ก่อน

BENCHMARK

Benchmark คืออะไร แล้ววัดยังไงให้แฟร์?

ความเร็วที่วัดได้ขึ้นกับ "รันโปรแกรมอะไรมาทดสอบ" — จึงต้องมีชุดโปรแกรมมาตรฐานที่ทุกคนใช้เหมือนกัน

Workload / Benchmark

ชุดโปรแกรมมาตรฐาน (workload) ที่ทุกคนใช้ทดสอบเหมือนกัน เพื่อเปรียบเทียบ CPU ต่างรุ่นได้อย่างยุติธรรม

ต้องอัปเดตทุก ~5 ปี

เพราะผู้ผลิต CPU อาจแอบออกแบบชิปให้ทำคะแนน benchmark เก่าได้ดีเป็นพิเศษ (โกงทางอ้อม) โดยไม่ได้เร็วขึ้นจริงในงานทั่วไป

ออกข้อสอบ!Benchmark = ชุดโปรแกรมมาตรฐาน · ต้องอัปเดต ~5 ปี · เพื่อกันการ "โกง" benchmark เก่า

REAL BENCHMARK

SPEC CPU2006 — มาตรฐานที่ใช้จริง

จากองค์กร SPEC — แบ่งเป็นชุดทดสอบงานจำนวนเต็ม กับงานทศนิยม

CINT2006

งานจำนวนเต็ม 12 โปรแกรม — เช่น บีบอัดไฟล์, คอมไพเลอร์, หมากรุก AI

CFP2006

งานทศนิยม/วิทยาศาสตร์ 17 โปรแกรม — เช่น พลศาสตร์ของไหล, เคมีควอนตัม

คะแนนทั้งหมดเทียบกับ เครื่องฐาน (base machine) ที่กำหนดให้ = 100

PEER INSTRUCTION 🧠

คำถามฝึกคิด: mult เร็วขึ้น 6 เท่า เป็นไปได้ไหม?

ลองคิดก่อนดูเฉลย — บทเรียนสำคัญเรื่อง "ค่าติดลบเป็นไปไม่ได้"

โจทย์

โปรแกรมหนึ่งรันทั้งหมด 100 วินาที ในนั้นมีคำสั่ง mult กินเวลาไป 80 วินาที — ถ้าอยากให้โปรแกรมทั้งหมดเร็วขึ้น 6 เท่า ต้องทำให้ mult เร็วขึ้นอย่างน้อย 6 เท่า ใช่หรือไม่?

คำตอบ: เท็จ (False) — เร่ง mult อย่างเดียวไม่พอและเป็นไปไม่ได้
1. อยากเร็ว 6 เท่า → เวลารวมต้องเหลือ 100 ÷ 6 ≈ 16.7 วินาที
2. ส่วนที่ไม่ใช่ mult = 100 − 80 = 20 วินาที ไม่ถูกเร่งเลย
3. ต่อให้ mult เหลือ 0 วินาที เวลารวมก็ยังเหลืออย่างน้อย 20 วินาที
4. 20 วินาที > 16.7 วินาที → เป็นไปไม่ได้ ไม่ว่าจะเร่ง mult แรงแค่ไหน

AMDAHL'S LAW ⭐⭐⭐

Amdahl's Law — เพดานของการเร่งความเร็ว

บทเรียนจากข้อ 16: การเร่งส่วนหนึ่งของโปรแกรม มีเพดานจำกัดเสมอ

การเร่งความเร็วส่วนหนึ่งมีเพดาน = สัดส่วนที่คุณ "ไม่ได้" เร่ง
ต่อให้เร่งส่วนนั้นแบบไม่จำกัด (เหลือ 0) โปรแกรมรวมก็เร่งได้ไม่เกินเพดานนี้

ตัวอย่าง mult 80%

ส่วนที่ไม่ได้เร่ง = 20 วินาที → ต่อให้ mult เหลือ 0 วินาที เวลารวมต่ำสุด = 20 วินาที (เร็วขึ้นได้ไม่เกิน 100/20 = 5 เท่า)

วิธีเช็ค "เป็นไปได้ไหม"

1. หาเป้า: เวลาใหม่ = เวลาเดิม ÷ ตัวคูณที่ต้องการ
2. หาเพดาน: เวลาของส่วนที่ไม่ได้เร่ง
3. ถ้าเป้า < เพดาน → เป็นไปไม่ได้
จำแบบนี้เร่งส่วนหนึ่งเร็วแค่ไหนก็ไร้ประโยชน์ ถ้าอีกส่วนหนึ่งยังกินเวลาอยู่ — ต้องดูว่าเร่ง "ส่วนที่กินเวลาเยอะที่สุด" ก่อน

WORKED EXAMPLES ⭐⭐⭐

โจทย์คำนวณ — จับมือทำทีละข้อ

แนวข้อสอบท้ายบท — ลองทำก่อนดูเฉลย

ตัวอย่าง 1 · 500 MHz → กี่ ns?

1. CT = 1 / rate = 1 ÷ (500×10⁶)
2. = 2×10⁻⁹ วินาที
3. = 2 ns

ตัวอย่าง 2 · CPU time

โจทย์: IC = 10,000 · CPI = 2 · CT = 1 ns
1. CPU time = 10,000 × 2 × 1 ns
2. = 20,000 ns = 20 µs

ตัวอย่าง 3 · เร่ง mult

โจทย์: 100s รวม, mult 80s, เร่ง mult 4 เท่า
1. mult ใหม่ = 80 ÷ 4 = 20s
2. รวมใหม่ = 20 + 20 = 40s
3. เร็วขึ้น = 100 ÷ 40 = 2.5 เท่า

ตัวอย่าง 4 · Weighted CPI

โจทย์: ALU 50% (CPI 1) · Load 20% (CPI 5) · Store 10% (CPI 3) · Branch 20% (CPI 2)
1. Σ(freq × CPI) = 0.5 + 1.0 + 0.3 + 0.4
2. = 2.2

IC × CPI × Clock Cycle Time — ต้องรู้ครบ 3 ตัวถึงทำนายเวลาได้จริง

Latency ≠ Throughput

เร็วในความหมายหนึ่ง ไม่ได้แปลว่าเร็วในอีกความหมายหนึ่งเสมอไป

User vs CPU time

User time ขึ้นกับการจัดคิวของ OS · CPU time ขึ้นกับตัว CPU ล้วน ๆ

Benchmark

ชุดทดสอบมาตรฐานเทียบ CPU อย่างแฟร์ · ต้องอัปเดตเรื่อย ๆ ไม่ให้ถูก "โกง"

Megahertz Myth

GHz เป็นแค่ 1 ใน 3 ปัจจัย — ไม่ใช่ตัวชี้วัด performance ทั้งหมด

Amdahl's Law

เร่งส่วนหนึ่งมีเพดานจำกัด = สัดส่วนที่ไม่ได้เร่ง

Weighted CPI

Σ(freq × CPI) — ใช้บ่อย ≠ กินเวลาเยอะ

performance(x)→1 / execution_time(x)
F เร็วกว่า S→n = time(S) / time(F)
CPU time→IC × CPI × Clock Cycle Time
Clock cycle time→1 / clock rate เช่น 500 MHz → 2 ns
Clock rate→1 / cycle time เช่น 2 ns → 500 MHz
CPI→Cycles Per Instruction — เฉลี่ยต่อ 1 คำสั่ง
Weighted CPI→Σ (freq × CPI) เช่น 0.5+1.0+0.3+0.4 = 2.2
ALU 50% CPI 1→กินเวลาแค่ 23% (ใช้บ่อย ≠ กินเวลาเยอะ)
